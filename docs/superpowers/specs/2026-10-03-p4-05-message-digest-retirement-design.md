# P4-05 消息摘要与幂等记录到期治理设计

**状态：**方案已确认，书面设计待用户评审；本文件不表示功能已实现。

**代码基线：**P4-04 `56b1bc21bd5ed719100ab4c3682a9412bbd08cc9`，草稿 PR #51。

## 1. 目标与已确认约束

在 P4-04 清空在线库消息正文的基础上，清空两处正文 SHA-256 摘要，减少低熵正文被猜测后比对摘要的风险。保留消息时间线、原始回执及幂等键，防止历史请求再次生成消息。法务保全继续暂停清理。

用户已确认：只有正文已清理、幂等记录到期且会话无有效法务保全时才能清空摘要；幂等记录至少保留 30 天；延续客户端消息 ID 超过 7 天返回 `410` 的协议；永久到期标记不因时钟回退而失效；采用会话锁、事务内保全复核和批次证据。

本增量的“幂等记录到期”指移除其内容摘要并转为永久到期记录，**不删除幂等键、消息行或回执元数据**。元数据仍占用存储空间，后续完整元数据归档或删除需要独立设计。

## 2. 方案选择

| 方案 | 结果与代价 | 选择 |
| --- | --- | --- |
| 清空两处摘要，保留到期标记和幂等键 | 不改变消息关联与序号；需要可空摘要、永久到期判定及成对更新约束 | 采用 |
| 永久保留摘要 | 保持当前查询，但正文猜测比对风险长期存在 | 不采用 |
| 删除幂等记录或整条消息 | 需要重设旧键重试、唯一约束、Outbox 外键及补拉时间线 | 后续独立设计 |

## 3. 到期条件与时间语义

一条消息必须同时满足以下条件，才可在本批次退役摘要：

1. 租户当前为 `active`，消息关联的幂等记录存在且两行尚未退役。
2. `messages.text_body IS NULL` 且 `body_cleared_at IS NOT NULL`。
3. 取得租户和会话锁后，以数据库 `clock_timestamp()` 取得本批 `retired_at`；`message_idempotency.expires_at <= retired_at`，且 `body_cleared_at <= retired_at`。
4. 会话没有任一 `released_at IS NULL` 的法务保全。

现有 `expires_at >= accepted_at + 30 days` 约束继续有效；新消息仍按当前代码设置至少 30 个 24 小时天，不新增租户可编辑的幂等期限。默认正文保留 365 天时，摘要通常在正文清理后才退役；正文期限缩短到 1 天时，摘要仍等待幂等期限届满。边界使用 `<=`，不按自然日截断。批次实际时间早于已记录的正文清理时间时跳过该消息。

正文已清理但仍有摘要的消息，在现有 UUIDv7 重试窗口内继续支持相同内容返回原 ACK、不同内容返回 `409`。法务保全阻断摘要退役，不延长客户端重试窗口，也不恢复已清理正文或已退役摘要。

## 4. 数据模型与不可逆约束

新增迁移 `000016_message_digest_retirement`：

- `messages.content_digest` 和 `message_idempotency.content_digest` 改为可空，两表各新增 `digest_retired_at timestamptz`。
- 每表的 CHECK 要求未退役时摘要为非空 32 字节且退役时间为空；退役时摘要为空且退役时间非空。
- 消息退役状态还要求正文已清理，且 `digest_retired_at >= body_cleared_at`。幂等退役状态要求 `digest_retired_at >= expires_at`。
- 同一消息的两处摘要在一个事务内清空，两个退役时间相同。采用延迟到事务提交检查的约束触发器，查询关联两行的最终状态，核验退役状态和时间一致；任意一侧退役时必须存在对应行。普通事务不能提交单侧退役或时间错配。
- INSERT 只允许未退役且摘要非空的新行；退役只能由已有行的 UPDATE 转换产生，不能直接插入无摘要的新消息或到期幂等行。
- 退役后触发器阻止摘要恢复、撤销或修改退役时间，阻止删除到期幂等记录，以及改变到期记录的关联键、原始回执字段和到期时间。消息正文的 P4-04 单向约束继续有效。未退役旧行和原有测试夹具不要求每条消息都已有关联幂等行；缺少该行的消息不进入清理候选。
- 新增幂等候选部分索引，按 `(tenant_id, conversation_id, expires_at, message_id)` 覆盖 `digest_retired_at IS NULL`；候选查询连接消息表复核正文清理状态。索引选择以真实 PostgreSQL 查询计划核验。

新增不可修改的 `message_digest_retirement_batches`，字段包括批次 ID、租户、会话、实际退役时间、实际退役消息数、最小和最大 `seq`、本批实际消息对应的最小和最大 `expires_at`。条数为 1～1000，序号与时间边界合法，最大到期时间不晚于本批退役时间；保留租户和会话复合外键。每条消息计数一次，两处摘要清空不计为两条消息。证据不含正文、摘要或人员字段；最小／最大序号不表示中间所有消息都已退役。

批次证据与两表更新同事务提交，禁止证据 UPDATE/DELETE。Down 先锁定两表和证据表，再检查退役状态或证据；任一历史存在即拒绝回滚，不能用空摘要替换原始摘要恢复旧结构。无退役历史时 Down/Up 可往返。迁移可能持有表锁，需部署窗口和锁超时评估。

## 5. 清理服务与事务边界

在 `internal/retention` 新增独立 `DigestWorker`，提供 `ProcessTenant(ctx, tenantID)`，返回已提交批次的 ID、计数及序号／到期时间边界。使用现有数据库接口、租户枚举与有限重试机制；正文 Worker 保持自己的批次事务，不把两种清理强制合并。

每租户每轮最多处理一个会话批次，默认 100 条，上限 1000。事务步骤：

1. 开始事务，在任何查询之前显式设为 `READ COMMITTED`；失败即中止，不能继承连接的可重复读快照。
2. 对有效租户取 `FOR SHARE`，复核租户状态。候选时间仅用于筛选，不作为最终更新条件。
3. 稳定按会话 ID 选择存在可退役消息且查询时无有效保全的会话，取 `FOR UPDATE SKIP LOCKED`，避免被保全或被占用的会话阻挡其他候选。
4. 取得会话锁后用新语句重新查询所有有效保全，再取数据库实际时间。保全存在则退出本批。
5. 按 `expires_at, seq` 选择有限候选；按选定顺序取得消息行、对应幂等行的更新锁。锁后重新复核正文、两表未退役状态、当前 `expires_at` 与实际时间。仅把最终合格行作为本批集合。
6. 对同一集合清空两处摘要并写相同退役时间。两表实际更新消息集合必须完全相同；数量或 ID 不一致即回滚，不能只记录较小计数。根据实际成功集合写批次证据并提交。

总体锁顺序为租户 → 会话 → 消息 → 幂等。多个清理 Worker 与法务保全沿用同一会话锁。`40P01` 整个事务最多尝试三次，每次重新读取租户、候选、保全和时钟；取消、证据失败或约束失败均不留下部分更新。

保全先取得会话锁并提交时，后续清理必须跳过；清理先提交时，后续登记保全只能保护剩余数据，不能恢复摘要。正文 Worker 和摘要 Worker 并发时，同一会话串行，摘要清理只接受已提交的正文清理结果。

## 6. 发送与补拉契约

单聊与群聊共用 `existingMessageACK` 的永久到期判定。身份校验、单聊参与者校验及群聊历史参与校验顺序保持现有规则，禁止未授权账号通过退役状态探测消息。

| 请求状态 | 行为 |
| --- | --- |
| UUIDv7 超过既有 7 天窗口 | 仍返回 `410`，与是否已退役无关 |
| 窗口有效且命中未退役键、正文摘要相同 | 返回原 ACK，`duplicate=true` |
| 窗口有效且命中未退役键、正文摘要不同 | 仍返回 `409 idempotency_conflict` |
| 因时钟回退等原因通过窗口校验，但命中退役键 | 返回既有 `ErrRetryExpired`／HTTP `410`，不比较摘要、不返回重复 ACK |
| 同一消息 ID 用于另一会话或另一发送者 | 沿用原有幂等键范围与身份／参与权限校验 |

两种发送事务都在任何查询前显式设置 `READ COMMITTED`，避免继承可重复读连接中的旧摘要快照。查重通过一个 SQL 语句读取关联两行的退役时间和可空摘要：任一退役标记优先返回到期；无标记而摘要缺失等不一致状态返回存储不可用，不能视为键不存在后重建消息。

查重以该语句的数据库快照为判定点：清理尚未提交时可以读取完整旧状态并完成原 ACK；清理提交后的新查重只能读到退役状态。已经开始的请求可能在清理提交后才把旧 ACK 发出，这不代表恢复了摘要或写入了新消息。不得通过第二次独立查询把新旧两表状态拼接比较。

退役键不再次分配 `seq`、预留限流额度、写入正文、幂等行或 Outbox。保留消息表唯一约束作为额外防线。新消息必须继续写入非空 32 字节摘要；迁移不允许新消息绕过该要求。两种补拉不读取摘要，继续按 P4-04 返回已清理正文的 `seq` 与 `redacted:true`，分页和 Outbox 关联不变。

## 7. 进程配置与运维

扩展现有 `im-retention-worker`，新增两个默认关闭／默认值明确的运维参数：

- `IM_DIGEST_CLEANER_ENABLED`：空或 `false` 关闭，仅 `true` 启用，其他值配置失败。
- `IM_DIGEST_CLEANER_BATCH_SIZE`：默认 100，允许 1～1000；非法值配置失败。

原 `IM_BODY_CLEANER_ENABLED` 与正文批量配置行为保持兼容。两个清理开关都关闭时不连接数据库；任一启用时要求数据库 URL。正文清理开关不隐式启用摘要清理，摘要清理可单独处理已有正文清理历史。

每轮只枚举一次当前有效租户；对每个租户依次执行已启用的正文批次和摘要批次，各有独立 5 秒上下文。一类批次失败不阻止同租户另一类或后续租户；父上下文取消则停止。保留现有成功／空轮 1 秒间隔及错误 1～30 秒退避，SIGTERM 正常退出。日志只含固定类别、批次与租户／会话 ID、计数，不输出正文、摘要、连接 URL 或原始数据库错误。

## 8. 验收矩阵

1. **迁移与不可逆性：**旧消息和幂等记录仍可读；32 字节与可空状态约束；单侧退役、错配时间、正文未清理、早于到期时间的退役提交失败；退役后恢复摘要、改标记、改回执字段及删除到期幂等行失败。无历史 Down/Up 成功，有任一退役历史或独立批次证据则 Down 拒绝，并覆盖并发清理期间的回滚检查。
2. **条件与计数：**正文已清理但未满 30 天不退役；正文未清理但已满 30 天不退役；到期恰好等于实际时间可退役；自定义更晚 `expires_at` 必须等待；退役时间早于正文清理时间跳过；缺少幂等行跳过；序号与时间不同序时证据仍按真实集合计数。
3. **幂等与协议：**通过真实单聊／群聊发送建立消息，验证退役前窗口内相同内容 ACK、不同内容冲突；退役后正常过期与时钟回退到原窗口均为 `410`。跨租户、非参与者与错误任职不能得到 ACK 或退役状态；消息、幂等、Outbox、`last_seq` 和限流计数不增加，补拉遮蔽及分页保持。
4. **并发与快照：**两个摘要 Worker 不重复计数；正文 Worker 与摘要 Worker 串行；真实保全登记／解除与清理竞争，多个案件解除一项仍阻断；租户停用复核；被锁最早会话不会阻挡其他候选；发送先读旧状态与退役后查重的判定点正确。数据库连接默认 `REPEATABLE READ` 时，两个发送事务和清理事务仍使用新快照读取已提交退役／保全。
5. **事务失败：**更新两表之一失败、集合错配、证据插入失败、取消、死锁有限重试都不留下单侧更新或无证据退役；重试期间登记保全必须阻断下一次尝试。
6. **进程：**四种开关组合、非法开关／批量、仅摘要启用、两个开关全关不连接数据库、一类失败另一类仍运行、后续租户公平处理、错误退避与取消；实际进程启停烟测及日志无敏感数据。
7. **回归：**真实 PostgreSQL 集成测试、必要的竞争检测、`go vet`、`go build`，以及既有单聊／群聊发送、正文清理、保全、补拉和浏览器实时／离线链路回归。未提供集成依赖而跳过的测试不得记为通过。

## 9. 部署与交付边界

部署顺序：暂停摘要清理 → 应用迁移 → 部署支持可空摘要与永久到期判定的 API／Worker → 确认全部 API 实例已升级 → 显式启用摘要清理。旧 API 可能把 NULL 摘要视为正文冲突，因此不能在新旧 API 混跑期间开始摘要退役。正文 Worker 可继续遵守 P4-04 规则；摘要清理启用前必须确认全量新 API 能处理 NULL 摘要。

启用摘要清理后不能回退到不认识退役状态的旧 API，也不能通过 Down 恢复摘要。发生问题时关闭摘要开关并部署兼容退役状态的修复版本。

本增量只清空当前在线 PostgreSQL 两处摘要。进程内此前读取的摘要、MVCC 旧版本、WAL／归档、备份、外部副本和媒体擦除仍需独立治理。消息与回执元数据、批次证据和审计仍保留。数据库超级用户禁用触发器或 TRUNCATE 的防护由权限治理承担；本设计不宣称满足完整数据擦除或生产容量验收。
