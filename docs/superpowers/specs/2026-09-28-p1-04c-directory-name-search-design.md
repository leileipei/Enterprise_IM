# P1-04c 普通通讯录姓名搜索设计

## 目标与范围

集团员工凭已验证的访问令牌和选定任职，通过姓名片段查找自己有权查看的同事。搜索权限仍由当前已发布的 `directory_view` 策略决定。此阶段只搜索 `users.display_name`，不开放职位、部门或集团工号的模糊匹配；工号精确查找沿用 P1-04b。

## 接口

`GET /api/v1/directory/users?q={姓名片段}&limit={1..20}`。`q` 去除首尾空格后须为 2～100 个 Unicode 字符，拒绝非法 UTF-8 与 NUL；`%`、`_` 和反斜杠按普通字符搜索。`limit` 默认 20。`employee_no` 与 `q` 不能混用，也不能传入未知或重复参数。

成功返回 `{people:[{id,display_name,employee_no,memberships:[...]}],has_more:boolean}`。任职字段与 P1-04b 相同，人员与任职按集团工号、人员 ID、任职 ID 稳定排序。空结果返回 200 与空数组。`has_more` 仅按**实际可见人员**计算，不反映隐藏候选数量。身份或选定任职错误沿用 P1-04b 的 401/403；审计与数据库故障返回 503。

## 授权、审计与查询边界

一个事务中先验证本人任职，读取当前策略快照，再按租户和转义后的姓名片段取得最多 501 名在职候选用户。超过 500 名时返回 `400 refine_search`，不返回部分人员；客户端需缩小关键词。这个阈值可表明匹配规模超限，不能据此推断人员身份或具体任职。随后按固定顺序锁定候选人员并重新读取当前工号，按新工号排序；再逐人列举、锁定当前有效任职，对每个任职进行 `directory_view` 判定并写决策审计。仅将允许且人员归属再次核对一致的任职及资料加入响应，再按可见人员计算 `limit` 和 `has_more`。

搜索请求另写一条不含原关键词的 `directory_name_search` 审计；所有判定、资料读取和审计在同一事务内提交。锁冲突和任何审计故障均失败关闭，不返回部分结果。当前方案适用于首版集团目录；后续规模化搜索需要经授权的索引与分页设计。

## 验收

测试覆盖同组织可见、跨组织隐藏与发布放行、强制拒绝、一人多任职、同名去重、隐藏候选不影响 `has_more`、通配符字面搜索、超宽关键词、跨租户、冻结/失效身份和审计失败。HTTP 测试覆盖令牌身份、严格参数、响应和错误映射；数据库集成测试覆盖策略及审计。
