# 集团基础模型首个开发增量

## 目标与范围

以 [v2.2 需求](../../../enterprise_im_group_v2_2.docx)第 3、5、6、11 章为准，交付可运行的 Go 工程、PostgreSQL 基础迁移及通信策略判定核心。此增量是 P1 的第一部分；不将健康接口或数据库测试误称为完整 IM 产品。

本增量覆盖 Tenant、Legal Entity、Organization、Department、User、User Organization Membership 和 User Department Membership。数据库直接保证同租户外键、运营组织法人归属、同用户同组织任职区间不重叠、同时仅一个主任职、部门任职归属和时间包含关系。部门任职的时间包含关系使用数据库触发器检查，并在组织任职更新时间复核。

策略判定核心接收已鉴权的请求上下文：操作、操作者任职、目标任职、当前时间和适用规则。它拒绝跨租户、失效任职与 hard_deny；仅允许有效且明确引用隔离规则 ID 的 exception_allow 覆盖该隔离规则；跨组织默认拒绝，必须有匹配的 allow 或 exception_allow；同组织默认允许，其他操作限制仍在调用方校验。策略核心只负责人员间通信边界，不承担身份认证、文件密级和群成员资格。

## 设计边界

- 使用 Go 标准库建立 HTTP 服务入口，仅提供 `/health/live` 与数据库探针 `/health/ready`。尚无认证与管理员权限体系，因此不开放业务写接口。
- 使用 `pgx/v5` 访问 PostgreSQL；SQL 迁移可由 `psql` 或项目提供的迁移命令执行。数据库约束是最终防线，Go 业务层须提供可理解的错误。
- 使用数据库中的 `tstzrange` 半开区间 `[effective_from, effective_to)`，结束时间可空。同一人同一组织的区间不得重叠；不同组织可并行任职，但同一时点至多一个主任职。
- `organizations` 的虚拟汇总节点不关联法人且不可任职；运营节点必须关联同租户法人。父组织、父部门不可跨租户或跨组织。
- 客户端和管理员 UI、SSO、消息、Redis、MinIO、HA、压测属于后续增量。服务端的配置只从环境变量读取，不内置测试账号或生产秘密。

## 可验证场景

1. PostgreSQL 接受一人双任职，拒绝同组织时间重叠和跨组织同时双主任职。
2. PostgreSQL 拒绝跨租户法人引用、跨组织部门引用、超出组织任职有效期的部门任职，以及缩短组织任职导致的悬空部门任职。
3. 策略判定：同组织允许；跨组织默认拒绝；指定隔离规则被有效白名单覆盖后允许；错误引用或过期白名单仍拒绝；hard_deny 永远优先；跨租户拒绝。
4. 健康接口：进程活跃时 live 成功；数据库不可用时 ready 失败，不报告可接流量。

## 本增量完成定义

Go 单元测试通过，PostgreSQL 集成测试在本地容器通过，服务可启动且两个健康接口的成功与失败行为可复现。验收报告必须说明本增量尚未实现哪些 v2.2 能力。
