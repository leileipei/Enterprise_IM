## 1. 目标与已确认范围

用户选择“受控追加导入（推荐）”。目标是在已有集团租户内，把经过验证的组织、人员与任职文件作为一个批次可靠写入；新增记录追加，完全相同的记录跳过，任何冲突整批拒绝。操作者必须是当前有效的集团管理员，成功结果与审计同事务提交，并能在响应中断后查询批次。

本规格推荐通过现有 OIDC 管理 API 同步执行，默认关闭；这些入口、并发、恢复细节已随本书面规格获用户确认。成功标准是数据库主数据、批次回执、审计三者一致，以及重复提交不会二次执行。

### 1.1 方案比较

| 方案 | 成本与取舍 |
| --- | --- |
| 现有管理 API + 同步事务，推荐 | 使用已有 OIDC 身份与集团管理员授权；批次查询解决提交结果不明，首版无需任务队列 |
| 独立直接写库 CLI | 数据库账号不能替代业务操作者身份，需要另建认证、授权与凭据管理 |
| 持久异步导入任务 | 适合更大文件，但需增加任务租约、重试、停机恢复和后台任务授权；留待规模需求明确 |

### 1.2 数据范围

沿用 P4-27/P4-29 JSON 九张数组与规范化规则，文件内部引用必须闭合，每文件仅一个已有租户。

| 实体 | 首版允许行为 |
| --- | --- |
| tenants | 恰有一个目标租户，必须与存量投影完全相同；禁止创建租户 |
| legal_entities、organizations、departments | 追加新记录；同主键同内容跳过 |
| users、user_organizations、user_departments | 追加新记录；同主键同内容跳过 |
| external_identities、admin_grants | 可为空或包含完全相同的已有记录；新增、修改、改绑均整批拒绝 |

禁止更新、删除、自动合并、身份改绑、自动授予管理权。状态与历史任职区间遵守原模型，未出现在文件中的存量保持不变。新人员不会自动获得登录身份；身份源接入由后续独立增量完成。

首版不提供 Web 导入页面、直接写库命令、定时同步、租户初始化、审批工作流或回滚已成功批次的接口。

## 2. 接口与可信身份

新增两个管理接口：

- `POST /api/admin/import-batches/{request_id}`：JSON 正文直接是原输入文档；request_id 为客户端生成的 UUID。
- `GET /api/admin/import-batches/{request_id}`：查询终态回执。

两者均要求单一 Bearer 令牌、单一 `X-Acting-Membership-ID`，租户与人员来自验证后的身份，不接受正文或查询参数指定操作者。文件租户必须等于可信身份租户。仅有组织管理员权限不足以使用导入与查询。两接口在读取导入正文或尝试批次锁之前先以短事务检查当前 group_admin；后续主事务再次核验并锁定授权，不把前置检查当作写入许可。没有权限的请求不能通过 busy 状态探查批次。

导入入口保留经过验证的令牌到期时间，以及签名验证后的 issuer/subject。对现有 VerifiedIdentity 增加仅供服务内部使用的身份来源字段，由 OIDC 适配器填写，不从请求 JSON 读取，也不在响应、日志中输出。到期时间或来源缺失时导入关闭失败，不推断默认值。

在写事务内锁定并检查对应 external_identities 映射：active、同 tenant/user；同时验证租户、人员、当前任职、所属组织/法人及 group_admin 授权均有效。锁定授权依据直到事务结束，提交前再按实际 UTC 时间核对令牌与任职、授权区间。数据库映射停用和授权撤销发生在锁定前时必须拒绝，发生在锁定后时等待事务结束，顺序须有并发测试证据。

不承诺 IdP 上游即时撤销已签发 JWT：保持现有本地签名、到期及数据库映射检查语义，首版不新增 IdP introspection。

请求预算取客户端取消、30 秒总预算、令牌到期三者最早值。JWKS 获取与首次签名验证在进入写事务前完成，不能在持有写事务锁期间启动远程身份源请求。

## 3. 组件职责与复用边界

| 单元 | 职责与边界 |
| --- | --- |
| importpreflight | 保持已有输入、标量、模型校验；不增加数据库写行为 |
| importcompare | 复用纯比较及来源归因；提取逐行 new/identical/conflict 决策，原报告计数从同一决策计算 |
| 事务投影读取器 | 接受调用方 pgx.Tx，在本事务读取和锁定投影；不自行提交，不拼接用户 SQL |
| importapply | 批次幂等、范围检查、插入顺序、数据库约束失败、回执编码；仅接受认证层创建的可信身份 |
| access 内部事务授权接口 | 对传入事务检查集团管理员并写固定审计；复用既有规则，不调用会自行提交的 deny 辅助函数 |
| httpserver 导入 handler | 限制正文、验证请求编号、认证适配、固定状态码、有限响应；不把数据库错误原文写入日志 |

P4-29 PGReader 自行打开只读事务且拒绝写角色，不能直接拿其快照再开始新写事务。新事务读取器与独立写入配置检查必须分开；旧 CLI 的只读权限检查、环境变量隔离、退出码和报告保持原契约。

首版使用现有 API 数据库池，以正式应用写角色执行。该角色需要投影 SELECT、行锁所需权限、六表 INSERT、回执及审计 INSERT。复用现有应用角色并不等于数据库凭据本身只能追加；禁止更新的边界由导入服务固定 SQL 和测试保证。运维直接 SQL 属于数据库管理权限范围。新检查拒绝 superuser、BYPASSRLS、目标表 RLS、无法支持的模式/列/约束/排序规则，不接受只读比较账号作为写入账号。

## 4. 原子事务与并发

采用 `SERIALIZABLE READ WRITE`。数据库约束是最终写入门禁，预检通过不能绕过唯一键、外键、区间排斥、CHECK 或触发器。

1. 认证及前置集团权限检查、限长读取、SHA-256、完整输入校验在事务外完成；不能持锁等待上传。
2. POST 从数据库池取得一条本次专用连接，在显式事务外尝试 `(tenant_id, request_id)` 的 session advisory lock；键按固定命名空间和完整 UUID 对生成固定长度哈希，碰撞只额外串行化，不改变回执的完整 UUID 主键匹配。未取得锁立即返回忙碌，不等待。取得锁的语句结束后才开启 SERIALIZABLE 写事务，确保库存和回执的首个事务快照在独占批次编号之后建立。
3. 在该事务内按当前权限检查已有回执；已有匹配终态则不执行比较或 INSERT，结束事务并回放原结果。写事务结束后在共享清理预算内显式释放 session lock，确认成功后才归还连接；释放失败、事务状态不明或连接故障必须关闭并从池移除，禁止携锁连接被下个请求复用。
4. 按“操作者组织任职 → 租户 → 操作者人员/组织/法人 → 身份映射 → 管理授权”的顺序锁定授权依据。使用现有关系的 FOR SHARE，全部在同一事务内完成。
5. 显式固定 pg_catalog search_path、UTC；九表 ACCESS SHARE 稳定结构。读取目标租户全部九表投影并按实体固定顺序、主键确定顺序锁定已有行 FOR SHARE，防止比较期间已有行被更新或删除。外租户占用只返回布尔结果，不锁定或输出其原文。
6. 校验结构、库存与合并模型，执行逐行比较及禁止新增身份/授权规则；禁止实体的 new 决策转为 conflict，问题码 PROTECTED_ENTITY_NEW，确保九表计数闭合。若有任何业务冲突，零主数据写入，插入 rejected 回执与 deny 审计，检查授权后提交。
7. 没有冲突时，在授权锁与投影锁之后建立写入 savepoint。仅对 new 的六表记录执行参数化 INSERT；不用 ON CONFLICT DO UPDATE、DO NOTHING、MERGE、UPDATE 或 DELETE。
8. 顺序为法人 → 组织父节点优先 → 部门父节点优先 → 人员 → 组织任职 → 部门任职。同层按主键稳定排序，输入数组顺序不影响执行。既有外键非延迟，不能依赖任意输入顺序。
9. 核对实际影响行数，提交前检查实际时间下的授权与到期，插入 applied 回执、allow 审计，再提交。

session lock 由连接持有，回执与业务写入仍由数据库事务保证原子性；进程/连接退出释放锁，不留下恢复任务。同编号 advisory lock 只协调导入请求，不假设其他业务服务或 SQL 管理员遵守。对已读行的共享锁、实际约束与 SERIALIZABLE 共同保护本批次；不使用全表写阻塞锁，不承诺外部非 SERIALIZABLE 任意写入也维持所有应用规则。

遇到 `40001`、`40P01`、锁超时或确定的事务取消，回滚全部事务并返回可重试状态；服务器不自动重试。客户端只能保持原 request_id、原字节正文重试，从头获取库存和授权，不混用旧快照。既有服务锁顺序不完全统一，死锁可能发生，因此不得把“无死锁”作为承诺。

保存点内实际 INSERT 的完整性约束错误可在成功 rollback-to-savepoint 后变成 rejected 回执；写入数必须归零。未知错误、事务不可恢复或审计写入失败则回滚全部事务，不伪造持久终态。自定义触发器的非事务外部副作用不受此原子承诺覆盖，首次部署应使用仓库迁移配置的数据库。

事务隔离与行锁依据见 [PostgreSQL 16 事务隔离](https://www.postgresql.org/docs/16/transaction-iso.html)及[显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)。SERIALIZABLE 失败须重新执行整个事务，不能仅重复失败 INSERT。

## 5. 幂等与持久回执

新增迁移 `import_batches`，只保存不可变终态，不创建 durable running 任务：

| 字段 | 定义 |
| --- | --- |
| tenant_id、request_id | UUID，联合主键；tenant_id 外键指向 tenants |
| actor_user_id、acting_membership_id | 可信操作者及本次行使权限的任职 UUID |
| protocol_version | 固定 `controlled_append_v1` |
| input_sha256 | 完整收到的原始正文 SHA-256，固定 32 字节；不保存正文 |
| state、reason | applied 或 rejected；applied 原因为 NONE，rejected 原因为 INPUT_CONFLICT 或 DATABASE_CONSTRAINT_CONFLICT；禁止任意字符串 |
| receipt | 有限且严格校验的 JSONB，结构版本、每表计数、有限问题位置、零原文 |
| completed_at | UTC timestamptz，终态记录生成时间，不宣称数据库物理提交时间 |

每 tenant/request_id 唯一，只 INSERT，无 UPDATE/DELETE 服务方法。回执数据库约束检查合法状态、协议、摘要长度和 JSON 类型/字节上限。普通服务不提供回执删除或过期机制；以后归档必须保持去重键，不得静默允许旧编号重用。

幂等匹配要求：同租户、同操作者人员、同 acting membership、同协议、同 SHA。同编号不同正文或不同操作者返回固定 `BATCH_KEY_CONFLICT`，不返回旧摘要、操作者和问题内容。正文仅空格变化也视为不同，避免悄悄引入语义哈希规则。

已持久 applied/rejected 的精确重试返回同一终态和原计数，不重新分类或写主数据，不产生第二条 applied/rejected 审计。读取/回放仍须验证当前 group_admin；授权撤销后不能通过旧回执继续获取内容。GET 允许同租户任何当前 group_admin 查询，不要求仍是原操作者；POST 回放绑定原操作者。

GET 使用应用写入主库，不走副本。通过前置权限检查后，它在 READ COMMITTED 短事务尝试同编号 transaction advisory lock：失败返回 202 busy；取得后检查当前授权，再读取终态。无记录返回 404 not_recorded，表示本次观察没有持久终态，不表示此后不会有新请求。安全恢复依赖编号去重，不能据此换新编号执行。

COMMIT 已发送后连接丢失、客户端断开或截止时间到达时，数据库可能已提交：不得将其标为 rejected 或 rolled_back。能发送响应时返回 503 `COMMIT_OUTCOME_UNKNOWN`，只能查询/重试相同编号。服务器崩溃后已提交的回执仍存在；未提交的业务行、回执与审计同时消失。接管异步任务不在首版范围。

## 6. 报告、错误与审计

回执用新协议，不改变 P4-29 报告中的 import_authorized=false 等字段。它报告本次已持久终态，不承担客户身份正确性证明。

- applied：每表 input/new/identical/conflict/inserted；conflict=0，六个可写表 inserted=new，三个只读实体 inserted=0。全部相同也提交 applied 零新增回执及一次 allow 审计。
- 比较冲突 rejected：保留完整分类计数，所有 inserted=0；最多展示 200 条固定问题，只含输入 entity/row/field 与原因，不输出 UUID 值、姓名、工号、issuer/subject、数据库内容。
- 实际 INSERT 约束 rejected：整体原因 `DATABASE_CONSTRAINT_CONFLICT`；保留此前已完整计算的候选计数，inserted 全零，不猜测未能安全归因的行。SQLSTATE、constraint/detail 不写入响应或常规日志。
- 库存不完整、不支持、超限：503 固定原因，无分类回执；不能将部分库存拿来执行或写入终态。

| HTTP | 情况 |
| --- | --- |
| 201 | 首次 applied 持久成功 |
| 200 | applied 回放或 GET 查询任一终态 |
| 409 | 已持久 rejected、编号不匹配、POST 同编号执行中；固定码区分 |
| 202 | GET 同编号执行中 |
| 400/413/422 | 无效编号/协议、正文超限、输入文档不合法；零业务写入 |
| 401/403 | 认证无效/过期、身份映射无效、无当前集团管理权限、文件租户不匹配 |
| 503 | 库存/配置不可用、可重试事务失败、审计不可用、提交结果不明；原因严格区分 |

数据库审计固定 `resource_type=import_batch`、resource_id=request_id，action=`controlled_import.apply`，outcome=allow/deny；reason 为固定枚举。计数在回执中保存。成功/业务拒绝回执与对应审计同事务原子提交，审计失败不得提交主数据。

未通过认证、输入解析失败或数据库不可用的请求不保证产生数据库审计；仅记录固定安全事件码和安全请求关联号。不得把原始 URL、令牌、输入/库存正文、DSN、SQL 错误、任意请求头写入日志。查询复用当前管理查询审计习惯；一次查询不新增 apply 审计。

所有响应 `Cache-Control: no-store`，先完整编码并核对上限，再提交；提交之后只发送已准备响应。响应发送失败不撤销已成功的事务。

## 7. 限额、部署开关与兼容

| 资源 | 首版限额 |
| --- | --- |
| 输入 | 10 MiB、10,000 行、16 层 JSON、单字符串 4,096 字节；拒绝压缩正文 |
| 库存 | 九表合计 20,000 行、规范化字段 64 MiB，单字符串 4,096 字节 |
| 合并 | 30,000 行；一次读取完整上限内库存，不分页绕过限额 |
| 读取 SQL | 最多 256 条，含授权、模式、库存、全局占用、回执查找；有界批量全局键查询 |
| 写入 SQL | 每行最多一条 INSERT，最多 10,000 条；另最多 32 条事务/回执/审计语句，不反复执行失败行 |
| 超时 | 总预算 30 秒；单 SQL 5 秒、锁等待 1 秒，均受剩余总预算与令牌到期限制 |
| 并发 | 每 API 实例最多 1 个导入正文/校验/写入请求；其他请求立即忙碌，不排无界队列；跨节点由批次锁保护 |
| 报告 | 最多 200 条展示问题、完整内部决策仍覆盖全部行，响应/receipt 最大 256 KiB |
| 清理 | rollback、session unlock、关闭全部清理共享最多 1 秒；失败连接从池移除，不能复用未确认事务状态 |

深层合法组织树仍支持到输入行数限制，采用迭代排序，不用无界递归。大批次在时间预算内无法完成时全部回滚，不能以部分成功绕过上限。服务限额不保证 10,000 行在任意机器上均可在 30 秒内完成，验收须给出专属夹具耗时和机器环境。

`IM_IMPORT_ENABLED` 默认 false。开启必须同时启用 OIDC、具备此迁移和正式写角色，启动时验证配置；不兼容时启动失败，不能静默安装无授权导入路由。关闭时两个导入路径返回 404；不影响已有管理接口及两个只读预检 CLI。

部署使用现有 API 数据库连接配置和 TLS 策略，不新增本地数据库写命令或隐式连接环境变量。迁移、导入服务先在专属测试库验证；真实客户数据导入、生产开启及迁移执行另行安排，不作为本阶段开发验收的既成事实。

## 8. 必需验收证据

1. 六表新增、九表一致跳过、任意差异整批拒绝、禁止新增身份与管理员授权、无租户创建；乱序组织/部门父子能按拓扑写入。
2. 当前集团管理员允许，组织管理员拒绝；伪造 tenant/user、过期/缺来源令牌、停用映射、冻结用户、无效任职、撤销/时间到期授权均零主数据写入。
3. 原编号同正文重复、并发重复、另一操作者、不同正文、重启后重试；同编号最多一个终态及一条 apply 审计。
4. 中间表 INSERT、外键/唯一键/区间/CHECK、审计/回执 INSERT 失败；验证六表未留下部分新增，并核对 rejected 或无终态的规定。
5. COMMIT 前确定回滚、COMMIT 已发送后断链、提交成功后响应断开、进程退出；查询与相同编号重试均不二次应用。
6. 对照并发更新已有组织父节点、修改任职区间、停用外部映射、撤销授权、抢占全局 UUID/自然键；用真实 PostgreSQL 验证阻塞/冲突/回滚，不以 advisory lock 冒充对全部业务写入的屏障。
7. SERIALIZABLE 首个快照须在取得编号 session lock 之后建立；验证前一提交在新快照中可见、session unlock/断链清理、池连接复用及 advisory 哈希碰撞只造成忙碌；40001/40P01/锁超时无自动重试、无残留。
8. 输入/库存/报告限额的边界与越界、取消、令牌临近到期、深树、并发入口限流、清理后连接可用；实际 HTTP 接口覆盖，不能仅调用纯函数。
9. 响应、日志、回执无凭据、原文、外租户内容和 SQL 错误细节；验证数据库审计与计数符合零写/成功语义。
10. P4-27/P4-29 原 CLI、组模型、access、完整 OIDC/HTTP 与 ACK 回归；迁移 up/down 在空白及已有迁移专属库验证。

证据固定源码提交、数据库版本/迁移、夹具角色、实际测试名称/计数、耗时、PASS/FAIL/SKIP；保留故障注入与红绿日志。现有 P4-29 完整仓库套件仍有 105 个具名失败、825 个具名跳过，不能把增量门禁通过写成整个项目或生产验收通过。本阶段设计文档未运行产品测试，也没有产生真实导入证据。
