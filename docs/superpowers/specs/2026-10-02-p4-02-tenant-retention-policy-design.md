# P4-02 租户消息正文保留期配置设计

## 目标与边界

v2.2 要求消息正文默认保留 365 天，允许租户上线前以审批记录配置不同期限。P4-01 已在单聊和群聊读取时遮蔽到期正文。本增量让两种补拉读取同一个持久化的租户期限，并提供受保护的集团管理员 API 查询、修改与审计。文件、物理清理、备份过期、法务保全及审批系统联动另行实现。审批引用只记录外部审批单号，服务端不验证外部审批结果。

## 数据与权限

迁移 000013 在 `tenants` 增加 `message_body_retention_days`（默认 365，允许 1～3650）、`retention_version`（初始 0）和最近一次审批引用、审批人、审批时间。三项审批字段全空或全非空，审批人受租户内用户外键约束。每次成功修改还向 `tenant_retention_policy_history` 追加版本、期限和审批元数据；数据库触发器拒绝修改或删除历史记录。Down 在任一租户已修改配置或存在审批历史时拒绝执行，以免丢失审批证据。期限是固定的 24 小时天数，与 P4-01 的计算一致。

只有当前有效、持有集团管理员授权的选定任职可调用 `GET` 和 `PUT /api/v1/admin/retention-policy`。PUT 采用严格 JSON：`message_body_days`、`expected_version`、`approval_reference`；拒绝重复字段、未知字段、非法 UTF-8 和无效转义。审批引用为 1～128 个字符，首尾不可有空白，禁止控制字符。版本不一致返回 409；无效输入返回 400；无权访问隐藏为 404；失效身份返回 403。请求只使用经 OIDC 验证的租户与用户以及经数据库验证的任职，不接受请求体中的租户/审批人。每次成功读写均与审计同事务提交；写入时记录执行人、审批引用和时间。审计失败则不返回配置，也不修改配置。

已有消息时拒绝延长租户期限（409），以免重新显示按较短期限已遮蔽的正文；仍允许经审批缩短期限。需要较长期限的租户必须在首条消息写入前配置。管理写入持有租户行锁；正常发送也会先持有该行的共享锁，因此配置和写入不会穿越上述检查。管理写入先对操作者任职加共享锁，再对租户行加排他锁，保持与结束任职的锁顺序一致；同租户配置写入先以事务级 advisory lock 串行化。

## 读取一致性

单聊和群聊在现有读取事务中，从已加 `FOR SHARE` 锁的租户行取得期限；管理写入在任职锁之后对同一租户行加 `FOR UPDATE` 锁，再重新验证管理员有效期、授权和版本。补拉在最终当前时间复核后决定正文是否过期。到期、历史授权拒绝和策略拒绝统一返回只含 `seq` 的占位；游标连续性不变。更改期限只影响后续读取，不删除消息、改变 ACK 或重发 Outbox。

## 验证

PostgreSQL 集成测试覆盖默认值、两种补拉的租户自定义期限、租户隔离、集团管理员与组织管理员、失效授权、版本冲突、逐版本不可修改审批历史、审计原子性、迁移回滚保护，以及与结束任职并发时的锁顺序。HTTP 测试覆盖可信身份、严格请求、错误码与 no-store。全量回归覆盖现有发送、补拉与实时用例。
