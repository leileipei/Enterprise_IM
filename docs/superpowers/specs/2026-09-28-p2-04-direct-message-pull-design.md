# P2-04 单聊消息补拉设计

## 目的与边界

在 P2-02 持久化消息和 P2-03 Outbox 基础上，提供认证后的单聊消息按 `seq` 补拉，作为未来 WebSocket 重连恢复的数据源。本增量只处理单聊文本；不包含 Gateway、群聊、文件、设备 ACK、保留期清理或审计员查询。成功响应表示数据库中的可见内容已返回，不表示实时投递完成。

## 历史权限依据

`conversations` 的当前任职会被后续 `start_chat` 重选，不能据此授权读取旧消息。新增 `messages.recipient_user_id`、`recipient_membership_id` 和双方发送时的组织 ID；发送事务在原有策略通过后写入当时的接收方与组织快照。发送方已有 `sender_user_id` 与 `sender_membership_id`。两个任职共同构成该单聊消息的历史参与证据，组织快照用于后续组织级强制撤权。旧消息无法从当前任职可靠反推当时的接收方，迁移保持新列为空，补拉时只返回不可见占位，待独立可信回填流程处理。

请求方须拥有有效租户、用户、当前任职，且是该会话固定用户对的一方。会话结束或普通通信策略变化不会删去已授权的历史参与证据。读取逐条检查当前已发布策略中针对 `send_message` 的有效 `hard_deny`：对消息当时任职对或请求方当前任职与历史对方任职生效时隐藏正文。为避免定向规则造成一方仍可读，本增量对两种方向都执行撤权；只针对通讯录等其他动作的规则不影响消息历史。冻结账户或失效的请求方当前任职拒绝整次请求。普通 `isolate`、白名单到期与 `send_message` 拒绝不追溯撤销已获授权的正文。

## 接口和顺序

`GET /api/v1/conversations/{id}/messages?after_seq=N&limit=L` 使用现有 Bearer 身份认证。`after_seq` 必填且为非负十进制整数；`limit` 可选，默认 100，范围 1～500。只接受这两个参数，不接受请求体。结果按会话 `seq` 严格升序，最多返回 `L` 项，额外读取一项确定 `has_more`。可见项含 `message_id`、`seq`、`sender_user_id`、`text`、`server_time`；不可见项仅含 `seq` 和 `redacted:true`。`next_after_seq` 是本页最后一项序号，空页等于请求游标。客户端以 `seq` 推进游标，以 `message_id` 去重；不得用 Redis Stream 的 ID 代替补拉游标。

服务只在同一数据库事务中验证身份、会话参与、当前 hard deny 并读取消息，然后记 `message_pull` 审计。审计写入失败时返回 503，不返回正文。无效身份为 403；缺失、跨租户、非参与会话均为 404；输入错误为 400。响应设置 `Cache-Control: no-store`。查询使用现有 `(tenant_id, conversation_id, seq)` 唯一索引。

## 验证

PostgreSQL 测试验证游标顺序与分页、双方可读、第三方和跨租户不可探测、任职重选后的旧消息、普通策略变更、hard deny、冻结、旧数据占位、审计故障。HTTP 测试验证严格参数、认证、映射和最小响应。该增量只覆盖 M03 的单聊文本补拉，不宣称群聊历史区间或端到端断线恢复验收通过。
