# P4-04 在线库消息正文清理设计

## 已确认目标与边界

用户已确认 P4-04 采用专用 Worker，按租户保留期分批清空到期消息正文；同一会话存在任一有效法务保全时暂停该会话清理。首次部署默认不运行自动清理，运维核对保留期与保全后显式启用。单聊、群聊继续保留消息行和连续 `seq`，补拉对到期或已清理正文只返回遮蔽占位。P4-03 的保全管理、P4-02 的租户期限与 P4-01 的读取遮蔽是本次基线。

本次“清理”是在线 PostgreSQL 当前可见消息版本的 `text_body` 置空，不表示磁盘安全擦除。PostgreSQL 的 UPDATE 会留下旧行版本，后续 VACUUM 才回收旧版本可占用空间；WAL、归档和备份需独立到期管理。P4-04 不处理文件、备份、WAL 清除、外部审批核验或客户环境合规验收。参见 [PostgreSQL 17 VACUUM 文档](https://www.postgresql.org/docs/17/routine-vacuuming.html)和 [连续归档文档](https://www.postgresql.org/docs/17/continuous-archiving.html)。

## 方案选择

1. **本次采用：保留消息行、清空正文列。** 增加不可逆的清理时间，按小批次事务执行。现有消息外键、Outbox、幂等 ACK 和补拉序号可以保持。
2. **不采用：删除消息行。** 现有幂等与 Outbox 外键引用消息，删除会破坏 `seq` 时间线与客户端缺口检测。
3. **不纳入本次：逐消息加密并销毁密钥。** 这需要改造写入、读取、密钥生命周期及旧明文迁移；可作为要求可验证加密擦除时的独立方案。

## 数据与迁移

`000015` 将 `messages.text_body` 改为可空，新增 `body_cleared_at timestamptz`。约束要求正文非空时清理时间为空；正文为空时清理时间非空。非空正文继续遵守原有 1～16384 字节及非全空白约束。触发器阻止已清理行恢复正文、撤销或改写清理时间。消息 ID、租户、会话、`seq`、发送者、`accepted_at`、Outbox 和关联行不删除。迁移可能需要对现有消息表短暂加锁；部署时先评估表规模、锁超时和索引构建耗时，不能把“在线清理”理解成无锁迁移。

新增按 `(tenant_id, conversation_id, accepted_at, seq)` 排序、只覆盖未清理正文的候选索引。新增 `message_body_clear_batches` 作为不可修改的 Worker 证据，记录租户、会话、批次 ID、当前保留天数、截止时间、实际清理时间、首末序号与清理条数，不写入正文、摘要或人员隐私字段。每批仅在实际清理了消息后写一条证据。证据与正文更新同事务提交；证据写入失败则正文更新回滚。Down 在存在已清理消息或批次证据时拒绝回滚，检查前先锁定相关表，防止并发写入穿过空表检查。

现有 `messages.content_digest` 和 `message_idempotency.content_digest` 是正文的 SHA-256 摘要。P4-04 保留它们，以维持现有重复发送内容判定与 ACK；低熵正文可能被猜测后比对摘要，因此本增量**不构成所有正文派生数据的删除**。摘要与幂等记录的到期策略需作为后续独立增量设计，不能在本次直接删除幂等行：消息表仍对 `client_msg_id` 有唯一约束，删除幂等行而不调整重试语义会造成重发冲突。

## Worker 与事务顺序

新增独立 `im-retention-worker`，默认不自动运行；仅配置 `IM_BODY_CLEANER_ENABLED=true` 时开始循环。批量上限默认为每会话每事务 100 条，配置只能缩小或增大到明确上限 1000；每次循环公平轮询当前有效租户，每租户至多处理一个会话批次，故一个租户的积压不会永久阻挡其他租户。没有候选或数据库暂不可用时退避重试，不忙等。启用和批量是运维开关，租户保留天数仍由现有持久化管理 API 决定。

一次批次的锁顺序与判断：

1. 开启事务，在任何查询前显式设为 `READ COMMITTED`，确保锁后检查使用新快照，不受数据库、角色或连接默认隔离级别影响；设置失败则中止。按可信数据库租户 ID 读取有效租户及 `message_body_retention_days`，对租户行取 `FOR SHARE`，使期限更新等待本批次结束；候选筛选只使用初步截止时间，不据此清理。
2. 从该租户选出有到期且未清理正文、并且查询时无有效保全的会话；按稳定会话 ID 顺序取一行 `FOR UPDATE SKIP LOCKED`。已被消息写入、成员操作或另一清理 Worker 锁住的会话暂跳过。查询排除有效保全会话，避免最早的被保全会话反复阻挡后续会话。
3. **取得会话锁之后**重新查询 `conversation_legal_holds` 中 `released_at IS NULL` 的记录，并以数据库 `clock_timestamp()` 取得本批实际清理时间、重新计算截止时间。若有任一有效保全，本事务不清理该会话；等锁期间跨越到期边界时，仍以取得锁后的时间为准。
4. 按 `accepted_at,seq` 顺序选最多一批未清理且 `accepted_at + 保留天数 × 24 小时 <= 本批实际清理时间` 的消息，将 `text_body` 置空并填入 `body_cleared_at`；仅根据实际 UPDATE RETURNING 的行写批次证据，提交事务。

保全登记、解除和 Worker 都通过会话行锁串行化。保全先取得会话锁并提交时，Worker 后取得锁会看到有效保全并跳过；Worker 先取得锁并提交时，之后登记的保全不能恢复刚被清理的正文，管理文档继续提示“保全应在清理前登记”。事务失败、取消或证据插入失败都不提交任何部分清理。数据库死锁应整体回滚后有限次数重试，重试必须重新读取期限与保全。

## 读取与幂等契约

单聊与群聊补拉必须能扫描 `text_body=NULL`，且在 `body_cleared_at` 非空时强制只返回 `seq` 与 `redacted:true`；不返回消息 ID、发送者、正文或时间，即使租户期限配置或读取时钟发生变化也不恢复可见性。现有保留期与策略遮蔽仍保留，`next_after_seq` 和 `has_more` 按消息行计算。已清理消息的相同 `client_msg_id`、相同内容重试仍返回原 ACK；不同内容仍冲突，且不重新写正文或 Outbox。Worker 不改消息状态、Outbox 状态、群成员区间或会话 `last_seq`。

## 验收

- 迁移：旧消息仍可读取；非空正文约束不放宽；已清理行不能恢复；有清理历史时 Down 拒绝，包括与清理并发的回滚。
- 边界：默认 365 天、批准后的 1～3650 天、精确等于到期时刻、到期前一瞬间、不同租户期限分别验证。
- 保全与锁：同一会话多案件保全、解除其中一项、登记与清理互等会话锁、两个 Worker 并发、租户期限更新与清理并发；没有越过保全清理的记录。
- 原子性：批次证据写入失败、数据库异常、事务取消均不留下半批清理；重复运行只处理未清理正文，不重复计数。
- 契约：单聊和群聊清理后的补拉仍保持连续序号与遮蔽字段；同一消息的幂等 ACK 和既有 Outbox 引用仍有效。
- 运维：未显式启用时 Worker 不执行更新；启用后轮询多个租户且不会因一个被保全会话长期饿死其他候选；批次日志和证据只含计数与标识，不含正文。
