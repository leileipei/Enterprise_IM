# P3-08 群文本消息可靠写入设计

## 目标与边界

在 P3-07 的群历史补拉之上开放群文本消息发送。沿用现有消息表、幂等键、会话序号、限流、Outbox 和读取审计。此增量不实现文件、撤回、设备 ACK、群列表或策略解除后的自动恢复。

## 接口

`POST /api/v1/groups/{group_id}/messages` 使用与单聊相同的 JSON 请求：`client_msg_id` 为 UUIDv7，`text` 为 1～16384 字节的非空 UTF-8 文本。成功返回 `message_id`、`conversation_id`、`seq`、`server_time` 和 `duplicate`；首次提交为 `false`，相同键和正文的重试为 `true`。无效请求 400，身份失效 403，群或成员不可用 404，同键不同正文 409，来源任职与当前群区间不一致 409，群被策略阻断 409，超期重试 410，限流 429，审计或存储故障 503。HTTP 不返回其他成员的身份或策略明细。

## 事务与授权

先核验可信身份及当前有效任职，再按单聊规则验证 UUIDv7 时间窗口和正文。锁定群会话行后，先确认发送者曾以所选任职参加此群，再查询 `(tenant_id, group_id, sender_user_id, client_msg_id)` 幂等记录；从未参加群的账号不能根据响应探测群状态。已提交的相同正文返回原 ACK，仍要求当前账号和所选任职有效，但不再检查群状态、限流或当前成员区间。新消息要求群状态 `active`，发送者拥有活跃区间且其 `source_membership_id` 与所选任职一致。群行锁将发送与邀请、退群、移除和转让串行化，因此退出时的 `leave_seq` 与新消息 `seq` 不交叉。

批量读取所有活跃区间的来源任职和当前策略版本，逐一验证任职有效，并按 `send_message` 检查所有不同成员间的双向通信。无逐任职规则时，同组织、同法人的成员共享检查结果；存在逐任职规则时逐对检查。任何成员对不合规时，同事务将群标记为 `policy_blocked`、记录拒绝决策和请求审计，不产生新序号、消息、幂等记录或 Outbox；已有阻断状态不自动解除。所有允许决策批量写入审计。限流行锁等待后即使返回 429，也按最新服务时间复核身份、成员与策略；写入限流、序号、消息、幂等摘要和 Outbox 后再次复核。若等待数据库锁时越过有效期，回滚暂存写入并记录拒绝，合规则提交并返回 ACK。与管理员任职变更发生 PostgreSQL 死锁时，整个发送事务最多重试三次，每次重新授权；事务未提交前不会返回 ACK。群消息不写单聊专属的接收人字段；补拉按群区间来源任职授权。Outbox 收件人解析须再次验证事件与数据库消息，并按该 `seq` 所在的成员区间返回全部历史收件人；不匹配的发送任职不产生群通知。实时事件只提示补拉，不携带正文。

## 验收

PostgreSQL 集成测试覆盖：首次写入与补拉、同键重试与不同正文、并发序号、退群和重新入群、错误来源任职、非成员/跨租户、非成员探测阻断群、`policy_blocked`、新发布的隔离或 `hard_deny`、其他成员对不合规、任职到期、数据库限流锁等待跨越策略生效时间、限流拒绝后的复核、任职锁环重试、UUIDv7 时间窗口，以及 Outbox 或审计失败时完全回滚。500 人群测试覆盖无规则与逐任职规则路径，并核对 499 条决策审计；本机单次耗时不能证明生产 P95。Outbox 测试覆盖入群、退群、错误发送任职的通知边界。HTTP 测试覆盖可信身份、严格 JSON、状态码和 `duplicate`。保留单聊发送、补拉和实时通知回归。
