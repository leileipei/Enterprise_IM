# P4-03 会话级法务保全设计

## 已确认目标与本次边界

集团客户需要在调查或诉讼期间，按会话暂停到期消息正文的物理清理。用户已确认按会话保全，并先交付可审计的保全管理，再开发正文清理 Worker。本增量覆盖单聊和群聊的保全登记、查询、解除、权限、审计和持久化状态；不执行物理清理。P4-01/P4-02 的读取期限仍生效：被保全的到期正文对普通补拉保持遮蔽，保全不会恢复可见性。

同一会话可因多个案件同时保全。只要存在一项有效保全，后续清理 Worker 就不得清理该会话的正文；一个案件解除不影响其他案件。已清理的内容未来不能通过新登记保全恢复，因此管理界面和 API 文档需要明确：保全应在清理前登记。

## 方案选择

采用两阶段方案。P4-03 先建立会话级保全状态及管理入口；P4-04 再以该状态作为正文清理的事务内前置条件。一次同时交付管理与清理会让不可逆删除和新审批链路在同一增量首次接受验证；离线手工标记则缺少统一权限、重试和操作历史。两阶段方案使管理及并发语义先得到独立验证。

## 数据模型与不变量

迁移 `000014` 新增 `conversation_legal_holds`。每条记录绑定 `(tenant_id, conversation_id)`，引用现有会话的复合唯一键，包含保全 ID、案件编号、登记请求 ID、登记人及任职、登记时间，以及可空的解除审批编号、解除请求 ID、解除人及任职、解除时间。操作者及其任职也受租户内复合外键约束。解除字段必须同时为空或同时非空。案件编号和审批编号均为 1～128 个字符的外部引用，首尾不得含空白，内部不得含控制字符；服务端保存引用，不联动验证外部审批系统。同一会话同一案件编号同时只能有一条有效保全；解除后可用新的请求 ID 再次登记同一案件。

`conversation_legal_hold_events` 逐项追加 `placed` 或 `released` 事件，保存租户、会话、保全、请求 ID、引用、操作者、任职和时间。租户内请求 ID 唯一，每个保全最多各有一条登记与解除事件。数据库拒绝更新或删除事件；保全主行的登记字段不可改，解除字段只能从全空变为全非空一次，不能撤销解除或改写审批证据。状态行、事件和现有 `audit_events` 在同一事务提交。Down 遇到任何保全或事件时拒绝回滚，以免丢失证据。

有效保全定义为同租户、同会话且 `released_at IS NULL` 的记录。该定义面向未来 Worker 使用，不改变消息行、Outbox、幂等记录或会话 `seq`。过期正文的当前读取遮蔽不因保全状态改变。

## 管理 API 与权限

沿用 OIDC 验证的租户、用户和 `X-Acting-Membership-ID`，只允许当前有效的集团管理员调用：

| 操作 | 路径 | 输入与结果 |
| --- | --- | --- |
| 查询 | `GET /api/v1/admin/conversations/{conversation_id}/legal-holds` | 分页返回本会话有效及已解除保全；不接受请求体 |
| 登记 | `POST /api/v1/admin/conversations/{conversation_id}/legal-holds` | 严格 JSON：`request_id`、`case_reference`；创建返回 201，完全相同的重试返回该保全的当前状态及 200 |
| 解除 | `POST /api/v1/admin/conversations/{conversation_id}/legal-holds/{hold_id}/release` | 严格 JSON：`request_id`、`approval_reference`；成功及完全相同的重试返回已解除结果 |

`request_id` 为调用方生成的 UUID，跨登记和解除操作在租户内唯一。使用已存在请求 ID 但操作、会话、保全、引用或操作者不同，返回 409；不同请求 ID 对同一会话同一案件重复登记有效保全，也返回 409。已解除的保全不能再次解除，除原请求的完全相同重试外返回 409；登记请求在其保全解除后重试，也只返回已有保全的已解除状态，不新建保全。外部审批引用不得作为请求重试 ID。列表默认每页 100 条、最多 500 条，按登记时间与保全 ID 稳定排序，返回不透明下一页游标；游标必须绑定当前租户和会话，且每页重新验证权限。

请求体拒绝重复或未知字段、非法 UTF-8、缺失字段、`null`、尾随 JSON 和过大内容。不得从请求体或查询参数接收租户、操作者或任职。当前身份无效返回 403；非集团管理员或不存在、跨租户会话返回 404；状态冲突返回 409。通过 HTTP 解析的服务操作按现有管理 API 契约记录允许或拒绝审计；格式错误的请求在路由层直接拒绝。审计不可用时不提交状态或事件，不返回保全详情。响应设 `Cache-Control: no-store`。P4-03 不新增普通成员、组织管理员或审计员的保全管理权限；独立审计员 Scope 待后续设计。

## 事务、并发与未来清理接口

登记和解除先验证并锁定操作者任职及其集团管理员授权，再按 `(tenant_id, conversation_id)` 锁定会话行，随后锁定待修改的保全行。若等待行锁，在实际写入前按新的当前时间重新验证身份、授权与会话归属。事件、状态和审计同事务提交；失败或中断整体回滚。并发登记相同案件由有效保全唯一索引裁决；并发解除只能有一次状态转移。

P4-04 清理 Worker 必须先取得租户期限与会话行锁，再在同一事务中检查是否存在有效保全、复核到期边界并处理一小批消息。保全管理与 Worker 均通过会话行锁串行化，避免“检查无保全后，登记保全却先提交”的竞态。Worker 只能移除正文并留下 `seq` 占位及仍需的关系行；不得删除消息行造成补拉缺口。具体清理批量、备份过期和恢复演练由 P4-04/P5 单独设计与验证。

## 验收与测试

- PostgreSQL 迁移测试：跨租户外键、字段完整性、有效案件唯一、事件不可修改、解除不可逆、有历史时 Down 拒绝。
- 服务测试：集团管理员可登记、列出、解除；组织管理员与跨租户访问被拒；多个案件中解除一个仍有有效保全；案件可在解除后重新登记。
- 重试与并发测试：相同请求 ID 和输入返回原结果，不同输入冲突；两个并发登记不能生成两个有效同案保全；两个并发解除只成功一次；锁等待后授权过期时不写入。
- 原子性测试：审计或事件写入失败时主行不变；失败的释放不能让未来 Worker 误认为没有保全。
- HTTP 测试：可信身份、严格 JSON、分页游标、状态码及 `no-store`。回归测试确认单聊/群聊到期遮蔽和游标行为不因保全改变。

本增量的通过只证明保全管理及未来清理前置状态可用，不表示消息已物理清理、备份已到期、客户审批系统已联调或生产合规验收完成。
