# P2-01 单聊会话发起设计

## 意图与边界

P1 已建立集团统一用户、任职、OIDC 访问令牌和通信策略判定。P2 的首个可交付增量让员工选择自己的当前任职及目标员工任职，经过 `start_chat` 策略后创建或复用单聊会话。此增量只承诺会话身份与授权持久化；消息、ACK、Outbox、补拉和客户端在后续增量实施。

## 会话身份与数据约束

单聊以同一租户中的两个不同 `user_id` 为唯一组合，按 UUID 升序存储低、高两个用户。两人即使各有多个组织任职，也只共享一个单聊会话；每次发起仍须选择明确的目标任职，本人的任职来自已验证的 `X-Acting-Membership-ID`。会话保存最近一次获准发起时双方选定的任职、策略版本、创建者、创建时间、状态和 `last_seq=0`。复用时只更新选定任职及策略版本，不重置 ID、创建时间或 `last_seq`。这份选定任职是后续消息授权的输入，不替代发送时的实时身份和策略复核。

新增 `conversations` 表，包含租户内唯一的会话 ID、`kind=direct`、状态、排序后的用户与对应选定任职、`last_seq` 和策略版本。部分唯一约束确保同一用户组合最多一条单聊；复合外键确保用户、任职、会话属于同一租户且任职确属对应用户。仅允许 `last_seq >= 0`。为未来群聊保留 `kind` 与非单聊字段为空的形状，但本增量不创建群会话。迁移可独立回滚。

## 发起与复用事务

服务输入是已认证的 `TrustedIdentity` 和目标任职 UUID，不能从请求体接受用户 ID、租户 ID、`scope_allowed` 或策略结果。单一 PostgreSQL 事务中按 ID 顺序锁定双方任职，读取双方用户、组织、法人和当前发布的策略，按 `start_chat` 判定。本人失效返回 403；目标不存在、跨租户、同一用户或策略拒绝统一返回 404。所有有效格式的尝试写入策略决策审计和 `conversation_start` 请求审计；审计失败、锁冲突或数据库错误不返回会话，统一映射 503。

判定允许后以用户组合唯一键原子插入或复用会话。并发请求只能得到同一个会话 ID；复用也重新判定当前策略。已终止或阻断的旧会话不会因发起请求自动恢复。事务提交后才向客户端返回会话 ID、当前 `last_seq`、策略版本、是否跨法人及判定原因。这里的跨法人标记是双方任职法人不同的事实；单聊是否允许仍由 `start_chat` 判定，不能借用建群的跨法人审批语义。

## HTTP 合约

`POST /api/v1/conversations`，要求 Bearer 访问令牌、`X-Acting-Membership-ID` 和 `Content-Type: application/json`。请求体只允许 `{ "target_membership_id": "<uuid>" }`，最大 1 KiB，无查询参数。成功统一返回 200：`id`、`type="direct"`、`last_seq`、`policy_version`、`cross_legal`、`decision_reason`。无效请求 400；未认证 401；本人任职失效 403；目标或通信边界不可用 404；审计与数据库故障 503。错误响应不泄露目标人员、策略规则或 SQL 细节。

## 验证与限制

PostgreSQL 测试覆盖同组织成功、按用户组合复用、多任职重选、跨组织默认拒绝与发布放行、强制拒绝、跨租户、自聊、任职与账户失效、租户复合外键、审计失败和两个连接并发创建。HTTP 与真实签名令牌链路覆盖输入和身份映射。P2-01 不声称已可发送消息；消息写入时必须再次检查双方当前任职与 `send_message` 策略，后续设计需处理组织调动后的会话上下文和历史区间。
