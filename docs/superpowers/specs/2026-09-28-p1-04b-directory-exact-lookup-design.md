# P1-04b 普通通讯录按集团工号精确查找设计

## 目标与范围

普通员工在选定本人任职后，用集团工号查找一个同事，并看到该同事当前允许其查看的组织任职。集团工号在租户内唯一。此增量只支持精确工号；姓名、职位和部门的模糊搜索及组织树浏览后续实现。

## 接口

`GET /api/v1/directory/users?employee_no={工号}` 需要与目录详情一致的 Bearer 访问令牌和 `X-Acting-Membership-ID`。请求只允许一个 `employee_no` 参数，去除前后空格后不能为空，最多 128 个 Unicode 字符，拒绝非法 UTF-8 和 NUL。成功返回人员 ID、姓名、集团工号与可见任职列表；每项含任职 ID、组织、职位、主任职标志及当前有效部门。不存在、已失效或全部不可见均返回相同的 404；认证层发现账号冻结或令牌无效时返回 401；账号已认证但选定任职失效时返回 403；审计或数据库不可用返回 503。

## 事务与授权

服务端在一个事务中，以租户和工号锁定候选用户，取得当前有效任职 ID，按固定顺序锁定本人和候选任职，读取当前已发布策略。锁定用户行时，新增或转入该用户的任职也会等待；遇到其他读取事务占用任职行时，本次查找失败关闭，避免锁顺序循环。对每个候选任职执行 `directory_view` 判定，只有仍属于该用户且工号匹配的允许项进入响应；每个判定写 `policy_decision_events`，每次查询另写一条不包含工号原文的 `audit_events`。全部审计与读取在同一事务提交；任一审计失败均不返回资料。查询不存在或无可见任职时同样写查询审计。请求不能声明 Scope、可见性或策略版本。

## 边界与验收

双任职人员可只显示其中一个可见任职；跨租户、冻结人员、失效任职和强制拒绝不可泄露；发布的跨组织放行只开放命中任职。HTTP 与数据库测试覆盖这些场景以及无结果审计、审计故障和签名令牌到查询的完整链路。普通目录模糊搜索、排序分页、客户 IdP 实际联调不在本增量内。
