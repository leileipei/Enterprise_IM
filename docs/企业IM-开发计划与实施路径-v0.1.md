# 企业 IM 开发计划与实施路径 v0.1

**规划基线：**[《Enterprise IM 集团型多组织需求与详细设计说明书 v2.2》](../enterprise_im_group_v2_2.docx)。本文件是项目排期建议，不表示需求已开发或性能已验证。

## 1. 项目目标与规划前提

目标是交付集团私有化 IM：一个集团租户下的多法人、多组织、多任职人员，按授权范围使用通讯录、单聊、群聊、文件和多端同步；管理员能够配置通信边界并审计；系统在多节点运行时能可靠写入、推送和补拉消息。

参考排期为 **44 周**，以完成试点、生产验收和分批推广为终点。假设有 10～12 名全职当量人员，范围含 Web、桌面端和移动端，客户能按计划提供组织数据、身份源、测试环境和试点用户。排期从项目启动日计，不含采购、外部审批和节假日等待；每次基线变更都要重新估算。

建议配置：产品负责人/业务分析 1 人、架构与后端 4 人、Web/桌面 2 人、移动端 1～2 人、测试 2 人、DevOps 1 人；UI/UX、安全与数据库专家按阶段参与。若仅有 6～8 人，或者要求三个客户端分别原生开发，预计整体工期延长到约 12～15 个月，应重新排程。

## 2. 推荐技术与交付路径

```text
业务规则与验收基线
    ↓
集团身份、法人、组织、任职、Scope、通信策略
    ↓
可靠消息事务链路：client_msg_id → seq → ACK → Outbox
    ↓
单聊、群聊、多端连接、断线补拉与历史访问控制
    ↓
文件、搜索、多身份源、管理后台和审计
    ↓
高可用、容量、安全、备份恢复、试点和分批推广
```

服务端建议从**按领域划分的 Go 模块**起步，WebSocket Gateway 和 Outbox Worker 独立部署；PostgreSQL 保存组织、策略、会话、消息和 Outbox 的事实数据，Redis 用于可重建的连接与缓存状态，MinIO 保存文件对象。统一的组织、授权与策略判定接口由所有业务入口调用。先完成单条纵向业务链路，再增加能力；是否进一步拆分服务，以容量测试和运维证据决定。技术选型以 v2.2 文档为基线，具体版本和客户端技术在第 0 阶段冻结。

## 5. 不得后置的质量与验收线

- **隔离与权限：**所有业务查询带 tenant_id；发起会话、发消息、邀请、搜索和文件下载执行统一策略判定。`hard_deny` 不可被白名单覆盖；任职失效和账号冻结后新操作立即拒绝。
- **历史访问：**以会话成员加入/退出序号区间决定可读正文；退群、调动、白名单过期、重新入群和文件权限变化分别验证，越权内容只能返回不可见标记。
- **可靠性：**`client_msg_id` 幂等、同会话 seq 唯一连续、消息与 Outbox 同事务提交。客户端 ACK 超时、Worker 失败、Gateway 重启和多节点并发均纳入故障注入。
- **容量默认基线：**5 万注册用户、5,000 在线连接、单群 500 人；持续 100 条消息/秒 30 分钟，峰值 300 条/秒 5 分钟。
- **性能默认基线：**写入 ACK P95 ≤ 500 ms、P99 ≤ 1.5 s；在线投递 P95 ≤ 2 s；500 条可见消息离线补拉 ≤ 30 s；冻结/离职/`hard_deny` 撤权 ≤ 5 s；目录变更 ≤ 60 s 可搜索。
- **运行默认基线：**服务月可用性 ≥ 99.9%；RPO ≤ 5 分钟、RTO ≤ 2 小时。消息正文与文件默认保留 365 天，审计 730 天。目标硬件、网络和正式变更以项目启动记录为准。

以上是 v2.2 的**待验证验收值**，不是现有系统实测结果。P0 要把测试流量模型、网络拓扑、数据规模、测量位置及故障注入方式写成可复现方案。

## 6. 首批工作包与执行顺序

1. 将 G01～G11、M01～M05、F01、N01 转为可运行的验收清单，并准备集团总部、两家子公司、跨法人事业部、双任职人员和白名单样本。
2. 明确身份上下文：统一 user、法人 ID、`acting_membership_id`、任职有效区间、Scope 和通信策略版本；先设计数据库约束和迁移，再做管理界面。
3. 完成“登录 → 查通讯录 → 选任职 → 策略判定 → 发单聊消息 → ACK → 推送 → 重连补拉”的最小纵向链路。
4. 扩展群成员区间、跨组织/跨法人判定及历史访问，再做多端客户端与文件搜索。
5. 用第 14 章指标进行持续压测和故障演练，最后试点、签收和分批推广。

每个工作包采用“需求场景与接口 → 失败用例 → 实现 → 自动化验证 → 评审 → 演示”的完成标准。下一步宜先细化 **P0/P1 的任务清单和接口/数据模型**，而不是一次性把全部 44 周拆成开发票据。

## 8. 主要风险与控制

| 风险 | 早期信号 | 控制措施 |
| --- | --- | --- |
| 组织树与法人关系被混用 | 跨法人事业部无法一致判定 | P1 使用独立 Legal Entity ID，双任职和跨法人样本先行验收 |
| 策略实现分散在各接口 | 搜索、发送、下载结果不一致 | 统一判定接口和版本审计，接口契约测试覆盖每个入口 |
| 消息状态早于持久化返回 | ACK 后丢消息或重复消息 | 以数据库提交为 ACK 边界；消息、幂等和 Outbox 同事务 |
| 三端并行导致协议漂移 | 同一游标或已读状态不一致 | 先冻结事件与错误码合约，共用协议测试和多端场景用例 |
| 压测与备份演练后置 | 临上线才发现容量与恢复不达标 | P2 起持续记录延迟和积压，P5 前完成至少一次故障注入预演 |
| 客户身份源或组织数据晚到 | P4 集成阻塞、试点延期 | P0 锁定接口负责人和脱敏样本，P1 使用可替换适配器联调 |
